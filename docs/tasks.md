## 1. Legend and rules

### 1.1 Status

| Mark | Meaning |
|---|---|
| `- [ ]` | not done |
| `- [x]` | done **and** verified by the wave gate (section 2) |
| `(blocked: reason)` | appended to the task line while it cannot proceed; the reason names the task id, contract request or human item (`H-nn`) it waits on |
| `[NC]` | "never cut" (plan 10, section 6): belongs to the three demo bundles, the ranked queue, the audit log, the eval or the cost telemetry |
| `[STRETCH]` | optional; only after every non-stretch task of the same agent is done; first to go when scope shrinks (section 6) |
| `[CR-nn]` | the task implements or depends on a contract request listed in section 4.2 |

**Status is updated only by the wave gate** (the orchestrator or the Opus reviewer after running the wave's exit check in section 2). An implementing agent never ticks its own box. Instead its final message lists `READY: <task ids>` with the command output that proves each, and `BLOCKED: <task id> (reason)` for anything it could not finish. The gate ticks what it verified and appends `(blocked: ...)` to the rest. A task that fails the gate stays `- [ ]` and goes back to its agent.

### 1.2 Task line format

```
- [ ] **T-<agent-id>-NN** What to do, one sentence. · Plan: <section> · Doc: <file §section> · Rule: `<rule_id>` (rule tasks only) · Done: <acceptance condition> · Files: <paths>
```

- `Plan` points at the master plan (not included in this repo); `Doc` at a file in this folder. Test ids such as `T-BS-RB-3` or "test 12" are the numbered cases of that doc's test plan.
- **Rule ownership.** A rule id is *owned* by the one task whose `Rule:` field names it. Appendix A lists all 52 rule ids of plan 4.1 to 4.6, the owning task and the file. Other tasks may mention a rule id in prose (for tests or references) but never in a `Rule:` field. `bs_running_balance` is implemented by `foundation` (wave 0); `rules-bank` then owns the file and its tests.
- Task numbers never change once issued. New work discovered later gets the next number.

### 1.3 Definition of done (applies to every task, so `Done:` only states what is specific)

1. The task's tests exist in the agent's own test files and pass offline: `uv run pytest <files>`. No network, no API key (`FakeLLMClient`), no wall clock (`FIXED_TODAY = date(2026, 10, 27)` through `make_ctx`).
2. `uv run ruff check .` and `uv run ruff format --check .` are clean for the owned files.
3. No `float` for money, no `date.today`/`datetime.now`/`datetime.utcnow`/`time.time` in `backend/app/checks/**`, `findings.py`, `score.py`, `queue.py`; extracted text is untrusted (never used in paths, SQL, shell, regex patterns, format strings or HTML).
4. Only files the agent owns are written (roster in architecture.md section 12 and the agent sections below). `pyproject.toml` and `uv.lock` are frozen after wave 0; a missing package becomes a contract request, never a `uv add`.
5. Anything not fully built is written under "Known gaps" in the feature doc (plan 0.6: an item counts as addressed only with a check on mock data, a flag with evidence in the UI and an eval row; otherwise it is a documented gap).
6. Every flag has a rule id, evidence, and a standalone first-sentence explanation (plan principle 1). Rule tasks also set the discriminator named in the scoring contract (CR-34).
7. The task's own doc is **not** edited except to append to its `## Contract requests` and `## Known gaps and honest limits` sections. All other changes to `docs/*.md` go through the reviewer or `integration-kyc` (architecture.md section 9, rule 5). Confirmed at R0 (architecture.md section 9, rule 5).

### 1.4 Rules of the road

- Python 3.12 managed with `uv` only: `uv sync`, `uv add`, `uv run pytest`, `uv run ruff`. Never `pip`, never `python -m venv`, never hand-edit `uv.lock`.
- Registries auto-discover (checks, extractors, classifiers, bundle builders, routers): add a file, never edit a shared index.
- Today's date is injected through `CaseContext.today`. Never hard-code or read it inside a check.
- Nothing is auto-approved or auto-rejected; only a person's verdict closes a case (plan principle 2).
- A claim in any document must come from the eval table, including misses (plan principle 6). The words "authentic", "verified", "compliant" and "complies" never describe the tool's output.
- Wave order is binding: a wave starts only when the previous wave's exit check is green (architecture.md section 9, rule 11).
