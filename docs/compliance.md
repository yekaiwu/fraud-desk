# Compliance documents and the generated check catalogue

Build spec for the three short compliance documents (`ai-inventory.md`, `regulatory-mapping.md`, `validation-report.md`) and the generated `check-catalogue.md` (plan 7, 12 "Compliance paperwork eats build time"). Contracts: [architecture.md](architecture.md), [data-model.md](data-model.md), [api.md](api.md). Evidence sources: [test-data-and-eval.md](test-data-and-eval.md). Plan refs point to the master plan (not included in this repo). All data is fictitious. Do not git commit.

## 1. Purpose

The tool is two things at once: a **control** that supports a bank's customer due diligence and lending checks, and an **AI system that is itself supervised** (plan 7). The deliverable shows both: what the tool does for the bank's obligations, and what a MAS-supervised bank would ask about the tool. Paperwork is capped at three short documents plus one generated catalogue, and every statement in them is backed by a named code artefact or marked as unconfirmed.

Every one of the four documents opens with this fixed caveat (plan 7.3): *"Our reading as students, not legal advice. Decision support only; a human decides. All data is fictitious."*

## 3. Interfaces

### 3.1 Status marks (apply to all three documents)

Every sentence that states what an instrument requires, or what the bank must do, ends with exactly one mark:

| Mark | Meaning |
|---|---|
| `[found]` | read in a source named in the same row (primary or the secondary source cited) |
| `[found, secondary]` | read only in a secondary source (plan 7.1 outsourcing row) |
| `[confirm]` | not read at primary level, or not researched; a person must check it |

A table row with an instrument, a figure, a date or a legal duty and no mark is a defect. Claims about **our own tool** carry no mark but must name an artefact (section 4.3). Section 4.2 gives the initial mark for every instrument; downgrading `[found]` to `[confirm]` is allowed, upgrading needs a primary-source read and a note in the document's change history.

### 3.2 `gen_check_catalogue.py`

```
uv run python backend/scripts/gen_check_catalogue.py [--out docs/check-catalogue.md] [--check]
```
`--check` writes nothing, exits `1` if the file on disk differs from the fresh output (CI use), else `0`. Without it the file is rewritten.

```python
# backend/scripts/gen_check_catalogue.py
PLAN_RULES: dict[str, str]                      # rule id -> plan section, the 52 rules of plan 4.1-4.6 (4.1:9, 4.2:8, 4.3:5, 4.4:5, 4.5:14, 4.6:11)
BUILTIN_RULES: dict[str, str]                   # {"doc_unreadable": "8.5", "doc_unclassified": "5.3"}  (core/builtin_checks.py)
ADDED_RULES: dict[str, str]                     # {"file_reuse": "0.4 duplicate detection (file hash), added at R0"}; listed with this reason under "Registered but not in the plan"
def collect() -> list[CheckMeta]: ...           # app.checks.registry.discover(); return all_checks()
def ruleset_version(checks: Sequence[CheckMeta]) -> str: ...   # MUST equal Provenance.ruleset_version ("rs-" + sha256 of sorted "rule@version")[:12]); reuse the core helper (Contract request 1)
def render_catalogue(checks: Sequence[CheckMeta], *, plan_rules: Mapping[str, str] = PLAN_RULES,
                     builtin_rules: Mapping[str, str] = BUILTIN_RULES) -> str: ...
def main(argv: Sequence[str] | None = None) -> int: ...
```

**Output format** (`docs/check-catalogue.md`), byte-stable: no timestamps, LF endings, final newline, a fixed sort, `|` escaped as `\|`, newlines in descriptions collapsed to one space.

```
<!-- GENERATED by backend/scripts/gen_check_catalogue.py. Do not edit; regenerate with: uv run python backend/scripts/gen_check_catalogue.py -->
# Check catalogue
<caveat line from section 1>
Ruleset version: `rs-xxxxxxxxxxxx` | Checks registered: N | Planned in the plan but not registered: M
## How to read this            (3 bullets: default severity is a starting guess recalibrated from the eval; coverage = checks that ran / applicable; "tamper" = the edit the check is meant to catch)
## Forensics                   (stage = forensics; ordered by rule)
## Rules (per document)        (stage = rules)
## Cross-document              (stage = crossdoc)
   each table: | Rule | Default severity | Applies to | Requires | Use cases | What it checks | Tamper caught | Version |
## Planned but not registered (gap, plan 0.6)
   | Rule | Plan section |        (PLAN_RULES minus registered; "None" if empty)
## Registered but not in the plan
   | Rule | Stage | Reason |     (registered minus PLAN_RULES; builtins and ADDED_RULES show their reason, anything else shows "unplanned"; "None" if empty)
```
Columns map to `CheckMeta`: `applies_to` sorted and joined with `, ` (`{"*"}` printed as `any file`); `requires` likewise, empty as `-`; `use_cases` sorted; `description`; `tamper` or `-`; `version`. Sort: stage heading order above, then `rule` ascending. The same data is served by `GET /rules` (api.md section 9), so the page and the API cannot diverge.

## 4. Behaviour spec

### 4.1 Rules for writing the three documents

1. Short: each document at most about 250 lines; tables, not essays. No marketing language.
2. Every figure is either a mark-tagged regulatory fact (3.1) or a measured number linked to `validation-report.md`.
3. Claims about the tool are written as "the tool does X (artefact)" in the present tense only if the artefact exists in the repo at the time of writing; otherwise under "gaps". The agent verifies each artefact path exists (glob) before writing the row; a missing artefact becomes a gap row, not a claim.
4. No document states that the tool "complies" or "is compliant"; use "supports", "aligns with the expectation that", "is designed to".
5. Dates in the documents are the `--today` of the eval run or the source's own publication date, never the wall clock.
